# YUME Agent Harness Roadmap 架构审计

审计日期：2026-09-16。审计对象：用户提供的 `C:/Users/chenglingxiao/Downloads/AGENT_HARNESS_ROADMAP.md` 全部 18 节，以及当前仓库中与其直接相关的实现。项目声明版本为 0.3.21，OpenCode 固定依赖为 1.18.21。[E1]

本文是审计报告，不是原 Roadmap 的替换稿。原文第 18 节的实施指令属于被审计材料，不作为本次修改代码的授权。此次没有修改产品代码、原 Roadmap，也没有运行模型任务、构建或性能基准。下文明确区分代码事实、架构建议和需要实测的假设；读取到测试不等于本次已运行测试。

## 审计结论

**产品方向可以保留，但不建议按当前 P0–P10 的顺序实施。最大风险是把已有 OpenCode Runtime 当作底层工具，再在 YUME 内重建一套 Runtime。**

当前需要的是：让用户选择工作目录、发起一个有边界的任务、看到实际动作、批准必要操作、拿到可核验的结果，并在窗口切换或执行中断后知道任务发生了什么。

当前不需要的是：预先建设完整 Planner、Executor、Tool Registry、十状态任务模型、通用 Artifact Storage、通用 Scheduler 和可执行角色包生态。

建议决策顺序：

1. 验证固定版本 OpenCode 在用户工作目录下的实际能力与权限边界。
2. 完成一个“读取 → 修改/生成 → 验证 → 展示结果”的纵向闭环。
3. 补齐运行归属、中断处理和可观察性。
4. 用真实第二种使用场景决定抽象边界。

**不是取消任务概念，而是先把任务做成已有执行引擎上的产品能力，避免任务概念反过来要求重建引擎。**

## 一、目标、当前阶段和证据

### 1. 产品目标与当前范围

- 最终目标：有角色、有记忆、能处理桌面实际工作的个人 Agent。Coding 是能力之一，不是产品边界。
- 当前真正缺口：用户工作目录接入、执行权限与目录绑定、任务跨 UI 生命周期的归属、真实过程与结果展示。
- 当前已经具备：模型配置、OpenCode 会话与异步请求、工具调用与审批、Persona/Skills 注入、受限 Memory、报表后台执行与本地存储、桌宠活动事件。
- 未来假设：任意桌面事件触发、跨应用主动感知、任务精确暂停续跑、多 Agent、可执行扩展包、复杂工作流。这些不能反推当前必须建立通用平台。

“能处理用户电脑上的工作”是产品愿景；“抽象成完整 Runtime”不是可验收的用户收益。

### 2. 实际调用链

当前交互式执行：

```text
ChatApp
  → 组织 Persona / Skills / Memory / 附件 / 业务指令
  → OpenCode session + prompt_async
  → OpenCode 执行工具和模型循环
  → SSE message / tool / session 事件
  → ChatApp 更新文本、工具反馈、桌宠状态
```

前端已具备创建会话、异步发送、中止、订阅事件等薄客户端；不是只有一次普通 Chat Completion。[E2][E3]

当前权限链：

```text
OpenCode 工具权限请求
  → Rust 查询并按 YUME Settings 判定
  → allow/deny 自动答复，ask 显示给用户
  → Rust 重新核对当前请求和当前策略
  → OpenCode 继续或拒绝执行
```

OpenCode 端对受控工具统一配置 ask，Rust 再落实 YUME 的 allow/ask/deny，未识别权限默认拒绝。它不是两个各自独立的最终执行器，而是一条已有的策略与执行协作链。[E4][E5]

当前有两种性质不同的后台行为：

```text
通用定时提示：Rust 定时检查 → 打开 Chat → 发 UI 事件 → sendText
工作报表：数据库待办 → Rust Runner → 独立 OpenCode Session
        → 禁用工具的模型生成 → 校验来源/格式 → 发布报表
```

报表已包含执行认领、重试、唯一 occurrence_key、来源快照和保护手工编辑的发布逻辑；不能以“只有雏形”概括。[E6][E7][E8]

### 3. 会改变 Roadmap 判断的事实

| 已核实事实 | 对 Roadmap 的影响 |
|---|---|
| 固定使用 OpenCode 1.18.21，已有异步执行与事件 | 先做协议/能力验证，不先自建 Agent Loop |
| sidecar 工作目录固定在应用数据目录；内置工具安装在该目录的 `.opencode/tools` | Workspace 不是单纯目录选择 UI；更换目录可能影响工具加载 [E9] |
| 当前策略默认 deny，显式禁用 edit/write/patch/external_directory/task | 工具不可用可能来自策略，不能直接据此新增执行器 [E4] |
| 桌宠已有 sessionId/requestId 关联和工具活动映射 | P3 不应当作从零建设 [E10] |
| ArtifactCard 固定渲染音频播放器，来源于附件转换流程 | 可复用下载/反馈经验，不能当作通用产物模型 [E11] |
| Skills 已从角色包读取并拼接进请求 | P10 的基础不是空白；当前更该控制输入体积 [E12] |
| Memory 已限制最多 8 条、1,200 字符 | 复用，不建第二套记忆/上下文检索基础设施 [E13] |
| history.json 存文本投影，完成回合时重写历史列表 | 不应再加第三份完整 transcript；现有历史也不是完整执行日志 [E14] |
| 通用定时入口依赖 Chat，权限自动处理也由 Chat 轮询触发 | 生命周期归属比新建文件夹更值得优先解决 [E5][E6] |

官方资料也说明 OpenCode 已提供内置文件/搜索/Shell 工具、会话与事件接口。[O1][O2] 这些资料用于确认复用方向；**不是固定版本在 YUME 当前配置下已经通过验证的证明**。

## 二、逐项分类审计

以下按影响优先级排列分类；“删除”指删除拟新增的工作，不代表立即删除现有用户数据或已发布行为。

### REDESIGN

#### R1. 重新定义 Agent Runtime 的边界，而非重建执行引擎

- **当前方案：** 第 3–4 节提出 Character / Agent / Harness 三层，并列出 planner、executor、tools、permissions、context、events 等新模块。
- **问题在哪里：** “缺 Agent Layer”的判断过于宽泛。模型循环、工具运行、会话和权限等待已有 OpenCode 承担。[E2][E4]
- **为什么复杂：** 再建一套规划与执行职责，会产生两个循环、两份工具状态、两套错误/取消语义，还要决定哪一方是权威。
- **更简单替代：** OpenCode 保持唯一执行引擎。YUME 只补一个宿主侧协调单元，负责入口、目录、请求身份、策略、观察和结果引用。三个概念可以用于解释产品，不必变成逐层转发的三个框架。
- **收益：** 删除大批重复实现，数据流更短；不额外增加一次模型规划调用；Agent 修改代码时只需定位明确的接入边界。
- **Trade-off：** 依赖 OpenCode 的协议和行为。因此应固定版本、集中协议适配、验证关键契约；只有发现明确阻塞且无法薄适配时，才考虑替换那一项能力。

#### R2. 将 AgentTask 缩成运行记录，拆开生命周期与展示阶段

- **当前方案：** 第 5 节一次引入独立 Task，保存 goal、plan、steps、artifacts、result，支持 10 种状态和 Pause/Resume/Retry。
- **问题在哪里：** thinking/planning/executing/verifying 是活动描述，waiting_permission 是当前待审批事实，它们不等同于任务生命周期。
- **为什么复杂：** 工具与文本可交错出现；不同事件到达顺序会让状态反复覆盖。一个 Task 内再复制会话中的计划、工具结果和最终文本，会制造同步责任。
- **更简单替代：** 当前一项工作绑定一个 OpenCode Session，一次明确执行请求对应一个 Run，用 userMessageId 标识。持久化目录和运行结果等宿主独有事实；工具明细从会话读取。只展示 running、completed、failed、cancelled、interrupted；需要真正排队时再加 queued。审批等待和活动文案从当前事实派生。
- **收益：** 少一层实体映射、少一批状态迁移，取消和恢复更容易解释。
- **Trade-off：** 暂不支持一个复杂任务跨多个会话的编排。这里是当前映射约束，不是宣称 Conversation、Session、Task 在语义上永远相同。

#### R3. Workspace 从“上下文集合”改为固定目录与可说明的执行边界

- **当前方案：** 第 7、14 节将 Workspace Context 与 Workspace Permission 分别列出，但没有具体约束目录切换、Shell、会话归属和内置工具加载。
- **问题在哪里：** 当前 sidecar 在私有目录运行，策略是全局的；新增用户项目必须同时验证目录、配置、工具发现与权限是否串用。[E4][E9]
- **为什么复杂：** 若直接更改进程 cwd 或全局权限，再加多个工作区，会导致运行中任务的目录/策略漂移。反过来，为解决它立刻加 Workspace Manager、沙箱平台和多进程池也过重。
- **更简单替代：** 首版每次运行绑定不可变的规范化目录，只允许一个交互式 Workspace 任务执行。优先验证 OpenCode 的请求/会话目录作用域及私有配置加载；没有证据前不承诺支持。实现 root/path 参数的可信校验，并保留 Shell 单独审批。
- **收益：** 把最可能导致返工的集成风险提前，避免做完 UI 才发现工具不可见或权限作用域错误。
- **Trade-off：** 限制并发和多工作区切换。尤其必须说明：设置 cwd、重定向 HOME、设置工具权限都不是操作系统沙箱；任意获准 Shell 可以做超出目录的操作。若产品承诺“绝不能访问目录外”，必须禁用任意 Shell 或提供真实隔离，这项成本不能靠措辞省掉。

#### R4. 将 P0 和 0.4 的验收目标改为真实用户闭环

- **当前方案：** P0 以“产生 AgentTask 并通过 Event Stream 驱动 UI”为完成标准；第 17 节又把 Task/Runtime/Registry/Workspace/Timeline 列为最核心五项。
- **问题在哪里：** 用户可能看到更完整的进度，但系统仍然不能在选定目录完成工作。真正的修改与验证被排到 P4/P5。
- **为什么复杂：** 核心不确定性尚未验证，先承诺数据模型和跨模块接口，后续往往需要返工。
- **更简单替代：** 第一可交付版本直接完成两个样例：生成并校验一个非代码文件；在小项目修复一个问题并运行已有检查。两者走同一个 OpenCode 执行链。任务记录、权限反馈和产物展示只做到支持这两个闭环。
- **收益：** 更早验证产品价值，同时防止把 Desktop Agent 锁死为 IDE。
- **Trade-off：** 初期 UI 和任务管理能力有限，但每项能力都有可观察收益。

### REMOVE

#### X1. 删除拟新增的完整计划、步骤、事件、结果多份持久化

- **当前方案：** AgentTask 内嵌 plan/steps/artifacts/result，同时又建立 AgentEvent、Artifact Storage，并保留既有会话历史。
- **问题在哪里：** 同一工具完成、同一段输出、同一文件可能同时存在于 OpenCode、Task、Event、Artifact 和 Chat 中。
- **为什么复杂：** 每份副本都需要更新、重连、取消、删除和版本兼容规则；“单一事实来源”会变成长期同步工程。
- **更简单替代：** 执行事实以 OpenCode 消息/工具记录为准；文件以实际文件为准；报表以现有报表库为准；YUME 保存运行元数据、引用及自身产生的信息。事件用于通知，不另建事件溯源日志。
- **收益：** 减少存储、序列化、清理和迁移代码，避免为了展示而重建数据库。
- **Trade-off：** 历史恢复依赖 OpenCode 的保留策略，需要先验证。现有 history.json 不能立即删除：固定人设回复等本地消息并未进入 OpenCode，老数据也要保留。应分清执行事实与应用自产内容，而非强迫一切进同一张表。[E3][E14]

#### X2. 删除逐一包装现成工具的新增工作

- **当前方案：** 第 6 节列出 filesystem.*、shell.exec、git.status/diff/commit 等统一命名，可能被实现为 YUME 自有执行工具。
- **问题在哪里：** 对已存在的 OpenCode 工具再换名包装，并未增加产品能力；为每个 Git 命令建专用工具尤其没有当前依据。
- **为什么复杂：** 要维护两套参数 Schema、错误类型、权限名称和运行入口；单次调用多过一层边界。
- **更简单替代：** 保留原生工具 ID。展示中文名时用静态标签映射。Git 检查先通过受控 Shell，文件读写优先复用原生工具；仅 Worklog 等宿主独有业务保留自定义工具。
- **收益：** 不增加执行路径，不需要另一个工具生态和适配矩阵。
- **Trade-off：** 暴露少量 OpenCode 概念；未来确实需要更强的参数级约束或专门 UI 时，再为那个具体动作增加工具。

### MERGE

#### M1. 合并 Workspace、Filesystem Agent、Execution/Verification 的首个交付

- **当前方案：** P2 工作区、P4 文件能力、P5 执行验证分阶段建设。
- **问题在哪里：** 三者共同构成用户能完成一件事的最小闭环。独立交付目录树不能证明任务可完成。
- **为什么复杂：** 容易分别设计 Workspace Context、Filesystem Service、Executor 的接口，再花时间把它们拼起来。
- **更简单替代：** 一个纵向切片同时接通目录选择、必要原生工具、权限、已有检查命令和结果。文件树、依赖视图、项目类型识别不作为前置条件。
- **收益：** 先验证最短数据流，减少无消费者的接口和中间状态。
- **Trade-off：** 同一切片跨前后端，但范围由一条用户路径限制，不等于一次大重构。

#### M2. 合并 Timeline 与桌宠活动的事实判定

- **当前方案：** 第 8–9 节/P3 拟用同一 Event Stream 驱动 Timeline 和动画。
- **问题在哪里：** 方向正确，但现有代码已经有工具事件、PetActivity 和另一套 mood 通知，不能再平行增加第三套状态判定。[E3][E10]
- **为什么复杂：** 多个消费者各自推断完成/出错，容易把旧请求的事件误认作当前状态。
- **更简单替代：** 同一处按 sessionId + requestId 归属执行事实，Timeline 和桌宠分别读取这一投影。沿用现有 Tauri 事件机制，不新增消息总线；动画播放计时仍归 UI。
- **收益：** 减少重复判断，阻止 UI 动画成为任务状态权威。
- **Trade-off：** 需要一次小范围归并并保留已有请求过滤、终态判定和迟到事件测试；不能直接删掉这些看似重复的保护。

#### M3. 合并通用执行接入，保留报表的领域流程

- **当前方案：** P7 统一 Schedule、Worklog Report、Background Session 到 Agent Runtime。
- **问题在哪里：** 当前通用定时任务经 Chat 转发，确实需要改；报表流程却已有独立持久化和可靠执行，不能一并替换为“创建 AgentTask”。[E6][E7][E8]
- **为什么复杂：** 若统一模型、调度、来源快照、发布和人工编辑，Runtime 会承担大量报表特例；若强行丢弃这些特例，又破坏现有用户功能。
- **更简单替代：** 首先让通用定时入口直接调用宿主执行入口；聊天和报表共享同一 sidecar。只有协议代码出现真实重复时才提取 Rust OpenCode 客户端。报表的生成、校验、重试、版本发布继续留在 Worklog。
- **收益：** 去掉“后台执行必须打开 Chat”的依赖，保留现有稳定性；不需要通用 Trigger 框架。
- **Trade-off：** 仍有多个有意义的业务入口和两种完成规则。它们共享执行引擎，不必共享全部生命周期和数据库结构。

### SIMPLIFY

#### S1. Tool Registry 简化为原生工具加小型策略映射

- **当前方案：** 统一 AgentTool metadata，包含 name、schema、riskLevel、defaultPermission、execute，再用 User/Workspace/Context Policy 判定。
- **问题在哪里：** OpenCode 已有工具 Schema 和执行入口；现有固定工具的 match/switch 并不是天然架构缺陷。[E4][O2]
- **为什么复杂：** 动态注册系统把有限工具表变成插件生命周期；riskLevel 还容易和 defaultPermission 形成两套近似状态，而同一 Shell/read 的风险依参数变化。
- **更简单替代：** 继续使用 OpenCode 的注册能力。YUME 仅维护少量宿主策略：已知工具、参数/路径边界、默认审批方式和显示标签。未知工具拒绝。没有插件热加载需求就不引入动态 Registry。
- **收益：** 不复制 Schema 和执行逻辑，容易查到“谁允许了这次动作”。
- **Trade-off：** 扩展一个宿主策略需要显式代码修改；当前有限工具集下，这比增加通用框架更可控。

#### S2. Context Builder 简化为有预算的按需取数

- **当前方案：** 第 7 节列出目录树、重要文件、README、依赖、Git Diff、项目类型、相关文件等 Workspace Context。
- **问题在哪里：** 若被理解为每轮自动全部收集，会有重复扫描、无关输入、大 Diff 和陈旧缓存问题。
- **为什么复杂：** 很快需要“重要文件”规则、索引器、缓存失效和文件监听器来维护自动收集。
- **更简单替代：** 初始仅给目录、用户明确材料、必要 Persona 和受限 Memory；Agent 按当前问题调用 read/search。需要 README、Git 状态或脚本时再读取，并限制大小。Skills 也纳入总输入预算，先限制/显式选择，不先建向量检索。[E12][E13]
- **收益：** 同时减少文件 I/O、模型输入量和错误上下文，数据更接近当前状态。
- **Trade-off：** 部分任务多一两次工具调用；是否改善总时延需实际测量。重复访问真实成为瓶颈时再考虑缓存。

#### S3. AgentEvent 保持薄投影，不变成第二套协议

- **当前方案：** 新建统一 AgentEvent，类型涵盖 thinking、plan、tool、permission、artifact、message 等，data 为 unknown。
- **问题在哪里：** 原生事件已经存在；另建通用事件体系未必提供更强约束，unknown 反而把判断推给每个消费者。
- **为什么复杂：** 需要转换、版本化、全量重放、事件去重、迁移和两套工具状态匹配。
- **更简单替代：** 适配处只解析 UI 真正消费的原生事件，按既有消息/part ID 更新投影。通知只携带运行标识和必要变化；重连通过会话快照补齐，再合并后续事件。先验证快照格式、分页和竞态，不承诺任意事件重放。
- **收益：** 兼容性集中在一个小边界，UI 不遍布协议猜测。
- **Trade-off：** 不提供全量审计日志平台。当前权限 SSE 回退有针对 1.18.21 编码问题的注释，不能因“统一事件”就删除；须先验证该兼容需求是否仍成立。[E15]

#### S4. Artifact 简化为结果引用和少量展示分支

- **当前方案：** 第 10 节/P6 建立八类 Artifact、独立 Storage，支持 Open/Preview/Copy/Save/Apply/Revert/Compare。
- **问题在哪里：** code/markdown/report 是内容或业务类型，file/image/webpage 是载体；task 又是运行对象。这些混在一个类型枚举里，能力矩阵会迅速扩大。
- **为什么复杂：** uri 与 content 同时可选会产生多种不完整或重复状态；已有文件和报表还要再复制一份正文。
- **更简单替代：** 当前只需文件路径引用、现有报表 ID、原生 diff 引用；MIME 决定预览方式。先提供查看、打开/定位、复制或导出。结果就在文件/报表库中，不另存正文。
- **收益：** 能立即交付成果展示，同时避免产物数据库和万能渲染器。
- **Trade-off：** 不提供通用 Apply/Revert。文件可能被用户随后修改，因此“当前文件”不等于不可变产物版本；需要固定版本时再显式保存副本。现有音频 ArtifactCard 保留专用行为，不机械泛化。[E11]

#### S5. Verification 简化为任务相关证据

- **当前方案：** 第 7 节和 P5 将 Understand/Modify/Run/Observe/Fix/Verify 描绘成标准循环，并有 verifying 状态。
- **问题在哪里：** 不是每项工作都要先规划、跑完整测试、构建再修改；文档生成和代码修改也没有同一种验收。
- **为什么复杂：** 如果做成固定流程或二次验证 Agent，简单任务也会承担额外模型调用和命令开销。
- **更简单替代：** 由同一 OpenCode 循环按任务选择必要工具。代码任务运行已有相关检查；文件任务检查实际生成、格式或用户给定约束。UI 展示命令、退出码和输出摘要。若没有检查，明确“未验证”。
- **收益：** 保留质量目标，减少无意义执行。无需通用 Workflow Engine。
- **Trade-off：** 验证规则需要按实际场景决定。模型说“完成”不能替代检查证据，session.idle 也不能独立证明目标达成。

### KEEP

#### K1. 保留“有身体的 Agent”和 Chat 只是一个入口

- **当前方案：** 第 2、4、9 节强调桌面人格、任务状态可见、Chat 不拥有 Runtime。
- **问题在哪里：** 原则合理，风险在于把原则直接翻译为多层框架。
- **为什么可能复杂：** 为每个入口建立接口族和完整适配器，而这些入口多数还不存在。
- **更简单替代：** 角色是展示与提示输入；宿主拥有任务生命周期；已有两个实际入口直接调用同一宿主函数即可。
- **收益：** 保留产品差异化，又不让窗口决定任务是否存在。
- **Trade-off：** 当前不会获得任意入口热插拔能力；没有这个需求就不付成本。

#### K2. 保留宿主权限、未知拒绝和审批时重新核对

- **当前方案：** 第 14 节由 Harness 决定安全边界，模型只提出工具请求。
- **问题在哪里：** 必须保留；粗粒度“Read 通常允许”不能替代具体文件/参数边界。
- **为什么不能再简化：** 只靠提示词或 UI 按钮会丢失实际执行约束；业务权限和文件/Shell 权限也不是一回事。
- **更简单替代：** 延续现有策略链，明确全局默认、会话范围和一次审批的优先级，在实际执行入口落实。减少重复配置源，而非删除校验。
- **收益：** 增加能力时不必重建授权系统，保持可追踪的决策。
- **Trade-off：** 权限处理和边界测试有不可省的代码量。审批明确拒绝后不能让模型换一个工具绕过。[E4][E5]

#### K3. 保留 Memory 与 Worklog 的现有领域约束

- **当前方案：** 复用 Memory、Persona、Worklog，并将报表纳入未来 Agent 能力。
- **问题在哪里：** 可复用，但不能把“更少模块”误解为把记忆、工作记录、执行日志合并成一套泛型数据。
- **为什么不能合并到底：** 用户记忆有确认和删除语义；报表有来源、版本和手工编辑保护；工具日志是执行证据，生命周期不同。
- **更简单替代：** 原库原职责保留，运行只引用这些事实；Memory 继续使用既有限额，报表继续保留去重/版本发布规则。
- **收益：** 避免无收益的数据迁移，减少隐蔽回归。
- **Trade-off：** 物理上仍然有多个存储。Single Source of Truth 应是“每种事实一个权威来源”，不是“全产品只能有一个数据库”。[E8][E13]

#### K4. 保留冻结扩张方向的决定

- **当前方案：** 第 16 节冻结大量 Chat 扩展、动画/角色、Voice 大系统、Marketplace、Multi-Agent、云同步、复杂 Workflow Editor。
- **问题在哪里：** 判断合理；但“Agent Harness 基础完成”是模糊的解冻条件，容易使基础建设无限延长。
- **为什么可能复杂：** 不断追加“基础能力”，每项未来功能都要求先造自己的基础设施。
- **更简单替代：** 将解冻条件写成明确任务成功率、可恢复性及真实使用需求；功能逐项证明价值，不一次解冻全部。
- **收益：** 团队工作量围绕用户结果，避免平台化惯性。
- **Trade-off：** 短期外观和生态扩张慢一些，但不影响已有功能。

### DEFER

#### D1. 延后精确 Pause/Resume 与通用自动 Retry

- **当前方案：** 所有 AgentTask 从一开始就能 Cancel、Pause、Resume、Retry。
- **问题在哪里：** 中止会话不等于暂停进程快照；继续发一句话也不等于恢复到未完成副作用之前。
- **为什么复杂：** Shell、写文件、发外部请求不天然幂等，自动重放可能重复执行；需要检查点、外部状态核对和恢复协议。
- **更简单替代：** 当前支持停止请求、查看已执行事实、用户明确发起一次新的继续/重试。中断后结果不明就标记 interrupted，先核对副作用，不能盲重试。报表原有安全重试继续保留。
- **收益：** 不承诺无法兑现的恢复语义，避免通用检查点框架。
- **Trade-off：** 用户可能需要确认继续；未来确有长任务恢复需求，再为具体动作设计，而不是先做万能恢复器。

#### D2. 延后完整 Workspace UI 与自动项目分析设施

- **当前方案：** P2 包含 File Tree、Important Files、Git Context、依赖和项目识别。
- **问题在哪里：** 当前任务闭环不依赖一个嵌入式 IDE，也不依赖持续维护项目结构快照。
- **为什么复杂：** 目录树监听、海量文件渲染、Git 刷新、项目类型推断引出许多新生命周期。
- **更简单替代：** 显示当前目录、必要路径和最终变更清单；由原生工具按需查询。只有用户实际导航需求出现后，再增加文件树。
- **收益：** 显著减少 UI 与同步工作，也避免后台扫描开销。
- **Trade-off：** 初期导航不如 IDE 丰富；不妨碍 Agent 完成选定工作。

#### D3. Desktop Context 先显式选择，广泛感知和 Computer Use 后置

- **当前方案：** P8 接前台应用、窗口、剪贴板、选择文件和浏览器，P9 加屏幕理解、鼠标键盘。
- **问题在哪里：** 隐式“这个”解析需要跨应用权限、平台适配和错误上下文处理，当前尚无使用证据证明优先级。
- **为什么复杂：** 常驻监听扩大数据与权限范围；Computer Use 又引入焦点、时序、坐标、重试和外部副作用。
- **更简单替代：** 先复用用户拖入文件、粘贴内容、手动附图和选择目录。未来一次验证一个高频上下文入口，按需读取，带来源和时间，不持久化全桌面状态。
- **收益：** 保留 Desktop Agent 方向，先获得低成本且明确的上下文。
- **Trade-off：** 不会自动理解所有“这个”；用一两个真实场景验证是否值得增加感知能力。若首发产品必须自动感知，则应把对应小型 Spike 提前，而非整个 Computer Use 平台提前。

#### D4. 延后可执行 Character Pack 与多事件调度生态

- **当前方案：** 第 12–13 节/P7/P10 扩展 Cron/App/File/Git/System Trigger，以及 tools/workflows/knowledge 的角色包。
- **问题在哪里：** 文本技能包与可执行插件是不同产品；已有文本 Skills 不意味着应马上增加插件执行权限。
- **为什么复杂：** 包版本兼容、工具生命周期、撤销、供应链和审批范围都成为宿主责任；多种监听还要防事件风暴与重复触发。
- **更简单替代：** 保留现有 persona.md、skills 文本、动画和受信内置工具。当前仅支持手动入口与已有明确 schedule 类型。等第二种真实触发需求、第二个必须执行代码的包出现，再设计共同部分。
- **收益：** 不新增插件平台、事件路由平台或 Workflow 编辑器，继续复用现有打包链。
- **Trade-off：** 第三方包暂不能运行任意代码；生态发展速度较慢，但核心任务能力不受影响。

## 三、性能与数据流：优先做更简单也更快的改变

这里没有运行基准，不能声称某个位置已经是性能瓶颈。以下区分可直接识别的成本与需要测量的优化。

| 结构或代码事实 | 更简单的方向 | 收益与边界 |
|---|---|---|
| 拟新增全量 Workspace Context | 按问题读取所需文件，限制输入大小 | 避免每轮扫描/序列化；总时延是否降低还取决于工具往返 |
| Skills 正文随 Persona 拼接 | 总预算、少量常用技能或用户明确选择 | 少发无关文本；暂不引入检索服务 [E12] |
| Chat 有 2,000ms 的最短回复展示门槛 | Agent 动作和审批立即展示；陪伴聊天可以保留节奏 | 消除任务反馈被人为延迟的情况；不是声称每个响应都额外慢 2 秒 [E23] |
| 权限 UI 每轮结束后等待 1 秒再次查询，allow/deny 也在查询过程中处理 | 在宿主接管运行时，复用已有权限事件来触发处理，并保留当前请求校验与重连补齐 | 减少轮询等待与无效查询；不得删除固定版本所需 SSE 回退 [E5][E15][E16] |
| 报表每 500ms 读取最多 200 条消息 | 当前低频业务可先保留；若已共享事件消费，再按需改为事件等待 | 不为了几条后台任务单独建设消息总线 [E7] |
| history.json 每次保存都会序列化整个历史列表 | 新增 Run 仅保存小记录，不再复制正文；确认历史瓶颈后再调整持久化粒度 | 全量写成本随历史总量增长，但尚无实测；避免一开始再造 Artifact/Event 库 [E14] |
| 拟让计划/步骤/输出同时进入 Task、Event、UI Store | 保存引用，UI 由执行记录派生 | 少序列化、少状态更新、少同步代码；收益方向明确，幅度未测 |
| 高频工具/文本事件触发 UI 更新 | 相同 part ID 原位更新投影，必要时合并短时间内更新 | 只有渲染测量显示问题时再节流/虚拟化；不要预先加第二层 Store/缓存 |

第一轮应测量：从提交到第一条真实活动反馈的耗时、输入文本量、工具调用数、审批等待时间、模型耗时、最终检查结果，以及较长会话下的 UI 响应。区分模型等待、权限等待和展示延迟，不能把它们都归为“Agent 慢”。

不建议当前新增：向量数据库、Redis、消息队列、中间服务、文件索引守护进程、通用缓存、多进程执行池。它们没有由本次任务需求或性能测量支持。

# Simplified Architecture

## 1. 最小但足够正确的结构

**一个 Tauri 应用，一个 OpenCode sidecar，一个很薄的宿主协调入口，复用现有领域存储。**

```text
Chat / 已有定时入口
        │
        ▼
Tauri 宿主协调
  - 运行标识与固定目录
  - 有限上下文组装
  - 请求提交 / 中止 / 状态读取
  - 策略与审批交互
        │
        ▼
现有 OpenCode sidecar
  - 模型循环
  - 原生工具和 YUME 自定义工具
  - 会话、消息、工具执行事实
        │
        ├── 实际文件 / 已有业务数据
        │
        └── 事件与会话快照
                  │
                  ▼
          宿主的轻量运行投影
                  │
             Chat / Timeline / Pet

现有 Worklog Runner ──► 同一 OpenCode sidecar
        │
        └── 原有报表校验、来源、版本和发布
```

“协调入口”和“运行投影”可以在同一个模块内，不要求各自一个 Service。模型规划、工具调度和执行循环全部留在 OpenCode，不在 Rust 再实现一次。

宿主多一次转发有明确目的：让执行和权限处理不依赖聊天窗口是否存活。它不是泛化中间件，也不是新网络服务。当前 API 客户端可用于 Spike；正式接管某条任务链后，只保留一个生命周期所有者，不能让 UI 和宿主同时提交、自动审批同一 Run。

首版限制：一个交互式 Workspace Run 同时执行；现有禁工具报表可保留独立会话，但必须验证目录与策略隔离。当前目录作用域支持若不成立，应收缩首版并发/工作区范围或做一个明确的接入修补，不默认引入 sidecar 池，更不能悄悄改变正在运行任务的目录。

## 2. 职责边界

| 所有者 | 应负责 | 不应额外负责 |
|---|---|---|
| React | 输入、审批选择、结果展示、动画计时 | 决定任务是否仍存在、维护第二套执行状态 |
| Tauri | 固定任务范围、宿主策略、运行归属、进程生命周期、持久化宿主事实 | 重新规划模型步骤、重新执行 OpenCode 内置工具 |
| OpenCode | 模型/工具循环、会话、工具记录、执行协议 | 报表手工编辑保护等 YUME 业务规则 |
| Memory / Worklog / Pack 模块 | 各自已有的业务事实和生命周期 | 变成一个泛型 Agent 数据层 |

优先把新宿主协调逻辑放在一个合理大小的模块中；共享 Rust 协议代码出现第二个真实调用者时再提取。不要按原文预先创建十一个文件，也不要为了文件更少把 Worklog、Memory 与运行器塞进一个大模块。

## 3. 最小数据模型

建议的 Run 只表达一次执行请求，具体字段在 Spike 验证后确定：

| 字段/关系 | 最小含义 |
|---|---|
| runId | 直接复用提交前生成的 userMessageId，不再多造一个可同步的 ID |
| sessionId | 对应 OpenCode 会话；一项工作中的后续请求仍可产生新 Run |
| workspacePath | 本次运行固定目录；当前不需要 Workspace 表与 workspaceId 映射 |
| createdAt / endedAt | 宿主实际观察到的起止时间 |
| outcome | 尚无终态，或 completed / failed / cancelled / interrupted |
| errorSummary | 仅有宿主错误或需要用户理解的失败信息时保存 |

用户输入、工具步骤、最终文本通过消息引用取得；文件/报表引用通过已知工具结果或业务回执取得。UI 列表真需要时才加标题索引；不预先保存一个会不断变更的 goal、plan、steps 和完整 result 副本。

没有 outcome **不自动等于当前仍在运行**：重启时需核对原生会话；无法确认就标记 interrupted。审批等待、当前工具、thinking/talking/working 都是可重建的展示投影。

第一版建议沿用宿主已有的 JSON 文件持久化方式，将最少元数据逐 Run 保存在应用数据目录，用原子替换避免半写入；不新建数据库服务。也不要将其塞进现有全量 history.json 正文，再随每个工具事件重写所有历史。未出现查询/规模需求前，不为“将来可能”迁移全部数据到统一 Agent 数据库。

报表继续使用其已有 report_runs；不要为了表面统一同时创建一条 AgentTask 并让两条记录同步状态。需要统一任务列表时读两种业务摘要即可，不必马上做统一写模型。

## 4. Single Source of Truth

| 事实 | 唯一权威来源 | 可以存在的派生信息 |
|---|---|---|
| 执行消息、工具输入输出 | OpenCode Session/Message/Part | UI 投影、短摘要、ID 引用 |
| 用户选择的运行目录、宿主中断原因 | YUME Run 记录 | 列表索引 |
| 当前未处理权限请求 | OpenCode 当前请求 | 宿主已核对的短期投影；点击时重新核对 |
| 权限意图 | YUME 配置与本次确认 | 转换后的引擎策略，不能独立编辑成第二源 |
| 真实文件内容 | 文件系统 | 路径、MIME、必要摘要 |
| 工作记录和已发布报表 | 现有 Worklog 数据库 | Report ID、卡片文案 |
| 用户记忆 | 现有 Memory 数据库 | 每次请求的有限上下文块 |
| 当前动画和过渡时间 | UI 本地状态 | 不回写为 Agent 生命周期 |

保留用户已拥有的聊天历史，以及只在本地产生的消息。这不违反上表；它们与 OpenCode 执行事实不是同一种数据。禁止的是同一事实出现多个可独立修改的权威来源。

## 5. 最少仍需明确的运行语义

- **完成：** 原生请求正常结束是运行完成证据；目标是否实现还要看该任务的文件/命令/业务回执。没有验证就显示未验证，不把 idle 映射成“全部成功”。
- **取消：** 用户点击停止后先发 abort；收到可确认的终止事实再记 cancelled。通讯失败不能当作已停止，应显示中断/待核对，已发生的外部效果不会因取消自动回滚。
- **恢复：** 窗口重新打开时读取状态和必要消息，再衔接实时事件；按原生 ID 去重，不存一套永久事件重放日志。
- **重试：** 用户明确启动新 Run；上次写入/外部操作结果未知时先核查。保留 Worklog 已有幂等回执机制，不把它误用成任意 Shell 的幂等保证。
- **权限：** 读取、写入和 Shell 分别确定范围；工作区目录本身不提供 OS 隔离。保持未经识别的工具拒绝。[O3]

# Simplified Roadmap

这是一份基于审计结果的精简建议，未覆盖或替换原 Roadmap 文件。

## 阶段 0：验证最大不确定性

**目的：证明当前固定版本能承载目标，而不是先建立 Agent Core。**

只做可丢弃的集成 Spike，使用小型临时项目与非代码文件样例，验证：

1. 用户目录如何传入并绑定会话，事件、权限和读取是否处于同一目录作用域。
2. 切换目录后，YUME 内置工具是否仍加载，`--pure` 与受控配置如何配合，是否误读其他配置。
3. 原生 read/search/edit/Shell 能否执行需要的闭环，哪些只是被当前策略禁用。
4. permission ID 与实际工具 ID/参数的关系，未知工具、目录外操作和 Shell 的实际行为。
5. 中止、断流、sidecar 重启与快照恢复的实际协议。

**一个已经可见的契约风险：** 前端 getSessionMessages 的类型和测试使用扁平消息 `{id, role, parts}`，Rust 报表客户端解析 `{info, parts}`，官方接口文档也描述后一种形状。[E20][E21][O1] 这尚未经过本次真实 sidecar 调用确认，不能直接宣判为现网故障；但它说明恢复逻辑必须对固定版本的真实响应做契约检查，不能只通过现有模拟测试。

**产出：** 一张实际支持/不支持的能力表与两个最小闭环的运行证据。

**退出条件：** 证明可复用的能力才进入正式实现；不支持时明确缩小范围或只修复那个接入点。不产生正式 Planner、Registry 或新数据库。

## 阶段 1：交付一个可用的 Workspace Agent

**合并原 P2 + P4 + P5，以及必要的 P0/P3/P6 子集。**

- 用户选目录并发送任务；每次运行目录固定。
- 使用原生工具完成读取、生成/修改和任务相关检查。
- 权限请求、当前动作、失败原因可见；可停止。
- 显示最终文件或变更及验证证据，支持现有方式打开/导出。
- 只做单交互任务执行；不做文件树、自动全仓库上下文、通用任务面板。

**验收：** 一个非代码产物和一个小型代码任务都能从输入走到真实结果；拒绝权限不会执行对应操作，错误不能显示成功，停止行为有明确反馈。

这一阶段就必须开始确认窗口生命周期；若任务会因 UI 生命周期丢失，不能把它宣称为稳定后台执行。

## 阶段 2：让任务归属和恢复可靠

**补齐原 P0/P3 中真正需要的部分，并提前处理 P7 的入口耦合。**

- 宿主拥有新任务的提交、中止、状态和审批处理，不依赖 Chat 轮询才能推进。
- 保存最少 Run 元数据；重开窗口可恢复展示；进程异常后明确 interrupted。
- Timeline 与 Pet 读取同一运行投影，保留请求身份过滤。
- 通用定时触发直接进入宿主执行入口，不先打开 Chat 再转发。
- Worklog 继续使用原有持久化和发布流程，按真实需要复用协议代码。

**验收：** 隐藏/重开 Chat、前端重载、sidecar 重启、定时触发与手动任务重叠、迟到权限答复都有明确行为；现有报表去重和手工编辑保护不回归。首版可以对新交互任务的并发请求直接返回“已有任务运行”，不必建立新队列系统；既有报表队列保留。

阶段 1 和阶段 2 可以在一次版本发布中连续完成；分开是为了先确认价值再收敛可靠性，不是让有生命周期缺陷的功能提前正式发布。

## 阶段 3：按测量结果改善质量和成本

- 处理实际出现的长历史、事件渲染、权限等待与输入体积问题。
- 删除 Agent 动作反馈不需要的固定展示等待。
- 只在真实产物需求下增加 diff 展示或一种预览能力。
- 只为已证明昂贵的重复计算考虑缓存；不建立通用缓存层。

**验收：** 有改前/改后的相关指标，改动没有新增第二个状态源，任务结果与现有业务保持正确。

## 阶段 4：按产品证据选择一个扩展方向

Desktop Context、额外触发器、可执行 Skills、Computer Use 都是候选项，不预先承诺它们必须按序全部建设。

先验证一个高频场景，例如用户主动分享当前文件/窗口材料；只有显式输入不足以完成任务时，才增加对应平台感知。只有文本技能不足时才讨论执行插件，只有直接工具/API 不足时才讨论鼠标键盘自动化。

**验收：** 新入口确实完成原来无法或难以完成的工作，并能复用既有执行链。不要以“插件数”“事件类型数”作为价值指标。

## 原 P0–P10 的去向与依赖

| 原阶段 | 原本解决的问题 | 审计处置 | 精简后的依赖 |
|---|---|---|---|
| P0 Agent Core | 请求成为可追踪任务 | REDESIGN / SIMPLIFY | 先契约 Spike，再最少运行记录；不自建 Loop |
| P1 Tool Registry | 工具发现与权限统一 | SIMPLIFY / REMOVE | 使用原生 Registry；必要权限映射随阶段 1 做 |
| P2 Workspace | 让任务操作用户项目 | KEEP / MERGE | 目录与工具加载验证后，与 P4/P5 同交付 |
| P3 Timeline | 过程可见、桌宠反馈 | MERGE / SIMPLIFY | 消费真实执行事件；不是文件能力的前置平台 |
| P4 Filesystem Agent | 读写用户文件 | MERGE | 优先接原生工具；在目录/权限验证之后 |
| P5 Verification Loop | 完成并核验实际工作 | KEEP / SIMPLIFY，提前 | 阶段 1 就必须出现；不增加第二模型循环 |
| P6 Artifact | 可使用的输出 | SIMPLIFY / DEFER | 基础结果引用随阶段 1；通用存储/回滚后置 |
| P7 Background Agent | UI 之外触发和执行 | MERGE / REDESIGN | 已有定时入口脱离 Chat 提前；泛化 Trigger 后置 |
| P8 Desktop Context | 理解用户当前材料 | DEFER，局部可用显式输入 | 先通过现有附件/粘贴/目录验证需求 |
| P9 Computer Use | 操作缺少直接接口的应用 | DEFER | 具体应用场景证明必要，再独立 Spike |
| P10 Skills Ecosystem | 专业能力分发 | KEEP 现有文本 / DEFER 执行生态 | 不阻塞当前闭环；真实扩展需求之后再建设 |

关键路径变为：

```text
固定版本和目录/权限契约
  → 真实任务闭环
  → 宿主生命周期与恢复
  → 有证据的性能/质量改进
  → 有需求的扩展
```

## 最小回归验证范围

这些是后续实施的验收要求，不是本次已执行的测试结果：

1. **目录与配置：** 两个样例目录交替运行，不串上下文、工具配置和审批范围；包含目录外路径及链接路径的边界案例。
2. **权限：** 允许一次、拒绝、请求已过期、运行中改为 deny、未知工具，都不会被 UI 陈旧状态绕过。
3. **真实闭环：** 文件确实生成/修改，检查确实执行；失败检查和未执行检查如实显示。
4. **生命周期：** UI 隐藏/重载不导致任务身份丢失；abort 失败不能显示已取消；进程重启不自动重放未知副作用。
5. **事件恢复：** 重复、迟到、断流后的消息按 session/request/part 归属；恢复不能依赖恰好只存在 200 条消息。
6. **已有业务：** Memory 关闭/角色隔离、报表独立会话/去重/手工版本、附件导出和现有角色包继续成立。

不需要因此构建新测试框架。协议行为用固定版本 sidecar 的少量集成用例，业务规则沿用现有测试，UI 走真实用户路径验证。

## 自我审查：如果再删除 30% 的架构和工作量

**如果相对原 Roadmap：** 删除自建 Planner/Executor、二次工具注册与包装、完整 Task 内嵌执行历史、通用 Artifact Storage、自动全量 Context 和首版 Pause/Resume，应该是最大的工作量缩减来源。但没有拆解估算，不能诚实地承诺恰好降低 30% 或某个更高比例。

**如果相对上面的精简方案：** 还可以削减首版范围，依次考虑：

1. 不做独立任务中心，任务就显示在现有聊天内。
2. Timeline 只展示关键工具/审批/结果，不做可视化 Plan 和复杂分组。
3. 产物只支持路径/报表链接与现有导出，暂不做内置 diff 或更多预览。
4. 只支持一个选定目录和一个交互任务；保留既有报表业务，暂不让任意定时提示获得新的 Workspace 写能力。
5. 新任务只保证识别中断、查阅已执行结果和手动继续，不提供自动恢复。
6. 不同时迁移老 Chat、老历史、所有报表流程；先让新增 Workspace 任务使用宿主入口，再按真实需要迁移。

这些可以减少 UI、迁移和扩展工作。它们**不会再删除一个必须存在的执行引擎或领域边界**，也无法保证总工时再降 30%。

不能继续删的部分：运行固定目录、真实执行权限、可靠的完成/中断语义、任务相关验证、现有 Memory/Worklog 数据保护。删除它们会改变产品正确性或丢失既有能力，不是架构简化。

**因此，精简方案在结构上已接近最小；继续明显压缩应主要缩小首发功能和迁移范围，而不是削弱正确性。**
