# 自动记忆、工作日志自动归档与聊天消息区清理施工方案

> 状态：代码已实施，自动化与隔离联调已验证；真实服务商模型的语义验收尚未完成。
> 日期：2026-09-28。
> 本轮已修改业务代码并增加数据库迁移；未替换日常安装的应用，未迁移用户正在使用的数据。
> 本地核对依据：当前源码及 `package.json` 固定的 OpenCode `1.18.21`。实际交付、测试结果与施工差异见 [验收记录](automatic-memory-verification.md)。以下保留设计目标供核对，不代表所有语义场景已经通过实测。

## 1. 交付目标与范围

用户正常聊天，助手自行识别值得延续的信息，之后自然使用，并能随用户的纠正、事情的进展而更新。用户不承担逐句选择、分类和保存的工作。

本轮交付：

1. 去掉每条消息下面常驻的“记住这件事”“保存到工作日志”“安排周五 17:00 周报”等操作。
2. 自动记住称呼、稳定偏好、长期要求，以及正在推进事项的重要背景、决定、进度和待办线索。
3. 新会话、应用重启和更换模型后，仍能在相关情况下延续上下文；信息有明确的用户、角色、项目和事项归属。
4. 用户纠正或结束一件事时更新记忆；用户要求忘记时真实删除，旧异步任务不能重新写回。
5. 设置页可查看、修改、删除、导出和关闭记忆；正常聊天不新增逐条确认、记忆提示卡或常驻状态条。
6. 聊天中明确的工作进展自动整理进现有工作日志，正确处理项目、日期、状态、更正和撤销。

用户已明确选择本轮同时完成自动记忆和工作日志自动归档。工作包 W 属于本轮正式交付，与自动记忆一起验收。现有明确指令触发的工作日志能力继续保留。记住“周五交周报”不产生定时任务，创建提醒、定时生成和发送仍需要相应操作意图。

不在本轮顺带回扫全部历史、同步多设备、建设新的云端记忆服务或改 OpenCode 内核。旧手动记忆保留；历史消息仍由原来的历史系统管理。

OpenCode 原生提供规则文件、会话历史和会话压缩；本次核对没有发现可直接启用、满足以上体验的完整自动长期记忆。官方自动记忆提案仍开放，生态中存在第三方记忆插件。因此采用 YUME 宿主管理记忆、OpenCode 提供原生会话和模型执行的路线。

## 3. 记忆应该记什么

| 类别 | 示例 | 生命周期与召回 |
| --- | --- | --- |
| 稳定个人信息与交流偏好 | 称呼、常用语言、回答简短、不要反复解释基础概念 | 精简的常驻背景；用户更正后替换 |
| 持续事项 | 正在准备答辩、推进某个功能、当前卡点 | 归入事项；相关时带入最近状态 |
| 决定与约束 | 已选方案 B；本次只设计不实施 | 区分事项约束与长期要求，记录适用范围 |
| 进度与重要事件 | 联调已完成、评审推迟、任务已经结束 | 有状态和时间；完成后退出“正在推进” |
| 角色共同经历 | 与某个角色形成的共同话题 | 保持原角色隔离 |

以下不自动沉淀：无关问答、寒暄、助手自述、助手未验证的完成宣称、假设题、引用中他人的偏好、附件内指令和临时要求的永久化。例如“这次展开讲”不覆盖“平时简短”，提到“某人喜欢咖啡”不成为用户喜好。

用户自己明确描述的事实可以直接成为来源；助手的计划和建议不能单独成为用户决定。任务执行结果只接受宿主确认的运行状态或可验证工具结果，失败、取消、半途输出不能记成已完成。

普通信息安静处理。沿用现有秘密信息拒存与敏感信息约束：自动路径跳过需要确认的信息，不为候选记忆主动弹窗；用户明确要求保存此类信息时，沿用必要的单次交互。提取前同样过滤，不能先发给提取模型再决定不存。

## 4. 技术主线

```text
真实用户回合 / 已确认的任务结果
    ↓ 只登记会话身份、消息标识、角色/项目/模型快照
宿主确认原生消息与回合状态
    ↓ 持久队列；去重、合并、恢复；正文按需从 OpenCode 读取
受限的结构化提取
    ↓ 提议事实、事项变更、证据标识；无文件/网络/业务工具执行权
Rust 校验、去重、更正与有回执的分支写入
    ├─ 个人事实 / 持续事项 → 本地记忆库与来源关联
    └─ 工作进展 / 工作计划 → 现有工作日志与来源关联
    ↓ 事项通过条目 ID + revision 引用工作事实
统一检索与上下文构建
    ↓ 稳定偏好 + 当前相关事项 + 少量相关事实
轻聊天 / 文件夹任务 / 原生工作台
```

### 4.1 宿主接管生命周期

- 轻聊天在 `promptAsync` 前登记回合：完整 catalog key、稳定 userMessageId、角色、目录、当轮已解析模型、记忆设置代次。登记不复制正文。登记失败不阻止聊天，只记录可恢复状态。
- Rust watcher 仅跟踪已登记的待处理回合；前端 SSE 可以催促检查，但不决定是否完成。切换会话、关闭聊天窗口后 watcher 继续运行，退出应用后由持久队列在下次启动恢复。
- 提交成功只代表请求已送达。确认必须核对原生 user message、assistant parentID、完成原因与在途工具；复用 Agent 已有的完成判定规则。
- 请求结果 unknown 时保留登记；明确未提交才取消。用户消息已存在但回复失败时，可以提取用户自己表达的稳定事实，不能采纳失败回复的结论；该分支必须与成功回合区分。
- Agent 在可靠的宿主快照/终态之后进入同一流水线；按原生用户消息去重，避免 UI 完成事件重放。
- 工作台由受管插件登记当前回合并通知宿主，宿主仍从原生 API 验证。插件钩子契约在工作包 0 验证；必要时采用目录受限的宿主事件观察器补足，不能靠扫描全部历史或前端页面常驻。
- 只有受管的真实用户会话可以进入自动提取。后台报告、内部提取请求、压缩、子代理中间回合、工具输出回放不再触发提取。

### 4.2 队列与模型请求

- 幂等键由完整会话身份、来源回合和提取版本构成，同时记录处理游标。算法升级默认不重放已处理历史。
- 待提取队列只保存来源标识、状态、代次与重试元数据；正文有界读取，用完释放。内存中的排队集合有上限，未处理工作留在数据库中按需领取。提取后若需要跨记忆/日志库恢复，持久化经过校验的有界派生变更批次和回执，不保存第二份聊天正文；详见工作包 W。
- 初始运行预算：全应用最多 1 个自动提取请求；同一会话空闲约 2 秒后合并相邻的新回合；每批候选不超过 5 条；模型单次总预算 30 秒；可重试故障最多 2 次并退避。用户请求优先，不抢占主聊天。
- 输入预算先按最近新增回合与少量关联上下文限制为约 6000 字符。长回合按完整消息/段落切批，不把截断后的前半句当完整事实，也不将未处理尾部标记完成。预算只是施工起点，通过工作包 0 实测后固定。
- 使用来源会话当轮已解析的服务商和模型。优先复用受管 sidecar 的模型调用能力，不新增账号或静默换服务商。后台调用产生的额外模型用量在设置说明中简短说明。
- 借鉴工作日志 `model_client.rs` 的禁工具调用，但独立定义提取协议、短超时、响应大小限制和取消；不直接套用其 300 秒循环。
- 内部模型会话必须有可信用途标记，在目录发现与工作台可见列表中排除，并在成功、失败、取消及重启恢复时清理。提取请求不带入人设、已有自动记忆或业务工具，防止自我循环。无法保证隔离和清理前不进入实际数据联调。
- 模型只能提交经过 schema 校验的提议：事实/事项、规范键、适用范围、证据消息 ID、有效时间、创建/更新/结束意图，以及工作条目的业务日期和状态。存储层重新校验证据归属及操作权限，不相信模型给出的作用域、置信度或任意记录 ID。记忆和日志分支有独立的设置代次、完成标记和回执。

### 4.3 存储扩展与连续事项

复用 `memories` 作为事实权威，新增版本化迁移。建议结构如下，最终命名沿用仓库约定：

| 扩展 | 内容与约束 |
| --- | --- |
| 范围 | 保留 global/persona，增加 workspace；项目使用规范目录对应的稳定身份，显示名不作为键 |
| 事项 | 增加 `memory_topics`：主题、所属范围、active/paused/completed、目标、当前进度、下一步和关联记忆；无文件夹的持续事项也可归属用户或角色 |
| 事实类型 | 增加决定、约束、进展等必要类型；区分稳定事实与事件，不将全部内容塞进 event |
| 来源 | 在 `memory_sources` 增加完整 catalog key、来源回合、来源性质；仅保存定位信息，不复制聊天正文 |
| 更新 | 规范语义事实键 + 目标修订号 + 来源时间/回合顺序；更新同一事实时替换旧版，迟到任务不能覆盖新信息 |
| 队列 | `memory_jobs` 和处理游标，记录领取、重试、处理结果、提取版本和有效代次 |
| 遗忘控制 | 已处理来源与删除屏障，只含不带正文的必要元数据；阻止旧队列和旧来源再次写入 |

事项摘要属于派生视图，必须引用有效记忆及其修订号；删除、更正后立即失效并重建。不能留下包含旧事实的独立摘要、向量、缓存或导出副本。读取到失效摘要时先省略，不继续用旧内容。

同名项目按真实目录隔离；全局个人偏好可以跨项目使用，项目进展只在本项目或用户明确提及该项目时召回。多个事项都符合“继续昨天那个”时简短澄清，不能擅自挑选或把几件事合成一件。

### 4.4 统一召回和失效

- 建立宿主 `TurnContext`：完整会话身份、角色、项目、当前用户文本、少量最近主题线索和设置状态。轻聊天、Agent、工作台共享同一检索函数与数据约束。
- 常驻部分包括用户明确的通用交流偏好和边界，不要求新问题恰好命中偏好里的关键词。常驻内容也有数量/长度上限，事项局部约束不能误升为全局。
- 覆盖“上一轮结束后立刻开新会话”的时间窗口：优先领取相关待提取回合，已完成且允许读取的最近来源可在同项目/明确事项匹配下提供少量临时原生上下文，经过同一删除屏障、过滤和预算限制。此补充只读、短暂，不伪报已保存；不能为等待后台模型无限延迟新回复，也不能通过测试里等待很久来掩盖问题。
- 相关部分按当前项目、活跃事项、别名、关键词和时间选择。提取时生成主题关联与同义表达；需要时对少量候选进行受限语义排序。
- 先用本地结构化索引与有界候选解决首版召回，不引入外部向量服务。固定同义改写验收未通过时，在本地补必要的召回能力；不能用“后续优化”代替跨会话验收。
- 以现有 8 条/1200 字符为基线进行分配与测量；必要时调整总预算，但不能把所有历史拼入 system prompt。近期已完成事项可在明确回顾时找到，不持续作为未完成任务带入。
- 更新、遗忘、关闭使用、角色/项目切换均增加上下文代次。修复 `yume_context` 只在启动时写文件的问题，工作台不能继续消费旧快照。统一一个权威注入出口，其他调用点改为委托；避免依赖人设前 64 字判断是否已经注入。
- 记忆作为有来源的数据进入上下文，不作为可以覆盖系统规则的新指令。过滤或存储失败统一降级：聊天、Agent 启动和工作台继续运行，错误状态在记忆页可查。

### 4.5 自然语言纠正与遗忘

- “以后叫我……”“改用方案 B”“这件事完成了”由提取/更新链识别，按照作用域和证据更新；“这次”只作用于当次或当前事项。
- “忘掉我的……”“这句别记”“记住这一点”等明确控制意图使用受限宿主工具。工具复用同一 service/repository，校验当前真实用户回合与目标范围；不依赖模型口头说“已经忘了”。
- 明确的记忆控制优先于后台队列。“别记这句”需要排除该来源，“忘掉”先使相关在途结果失效，再完成实际删除。指代不明确时只问要操作哪条，不凭模糊匹配批量删除。
- 删除已记事实，同时清理来源、检索索引、事项派生内容、缓存和临时提取会话；让已经运行的任务因代次失效而拒绝提交。以后确实出现新的用户陈述，可作为新来源重新判断。
- 本地长期记忆删除与原生会话历史删除是两个独立操作。工具回执明确删除的是记忆；同一会话原文仍由 OpenCode 管理，不能宣称已经从聊天历史、模型服务或用户导出文件中抹除。需要删除原文时走现有会话删除流程。

## 5. 消息区与设置页

### 消息区

- 删除常驻操作排、逐条记忆成功回执、依附旧按钮的敏感确认与相关 React 状态。
- 自动记忆成功不弹 toast、不出逐条卡片、不移动气泡位置；失败不在每条消息下面追加提示。
- 保留用户明确请求后的自然语言结果，以及真实工作日志操作的必要回执/撤销/查询结果。记忆内部提取任务不出现在聊天消息流、历史列表或 Agent 任务列表。
- 不全局删除 `chat-memory-*` CSS：工作日志回执仍复用部分样式。`memoryNotice` 目前承载多种非记忆错误，先拆清引用，保留会话不可用、发送未知等实际反馈。
- 视觉验收使用 420 × 560 逻辑像素、360px 压力宽度及大窗口，覆盖中英文和现有主题；移除控件后不留空白占位。

### 设置页

- 将“自动记录候选记忆”改成准确的“自动记忆”，不再承诺不存在的候选确认流程。
- 保留自动记忆与允许 AI 使用记忆的不同语义；关闭使用后，记忆分支的提取和注入都暂停。工作日志页增加独立的“自动整理工作日志”开关，日志分支按此开关运行；文案明确两者关系。关闭全部自动整理后不再发生此类后台模型请求。各分支重新开启均不默认回扫关闭期间的消息。
- 记忆列表显示事实/事项、适用范围、更新状态和来源入口；日常管理以当前有效信息为主。用户能编辑、忘掉一项、清空和导出；不要变成必须每天处理的候选收件箱。
- 新安装按本功能的自动体验默认开启。旧安装保留已保存的开关选择；目前旧 false 无法可靠区分默认值和主动关闭，不批量改成 true。在记忆页提供一次性说明/启用入口，启用后不逐条确认。
- 保留已有手动记忆。来源身份能唯一对应时补 catalog key；无法确认的旧记录标为 legacy 来源，不猜项目、不关联到同名 session。
- 迁移失败时保留原库，禁用自动流程并显示可诊断状态，不影响聊天。核查现有迁移备份的保留周期及清空记忆时的处理，避免遗忘后还留有应用管理的内容备份。

## 7. 必须通过的验收

| 场景 | 预期 |
| --- | --- |
| 问“你是什么模型” | 没有固定按钮，没有新增长期事实、日志或定时任务 |
| 说“平时回答简短点”，新会话问无关问题 | 仍遵守偏好，不依赖关键词巧合命中 |
| 接着说“这次详细讲” | 当次详细；之后不会永久覆盖简短偏好 |
| 连续几轮讨论一个项目，隔天新会话继续 | 找到目标、决定和最新进度，不需要整段重述 |
| 上一轮刚完成即开新会话，后台提取尚未结束 | 相关事项可按受限临时来源续接，不等待长后台调用、不用失效来源、不谎称已存 |
| 两个目录名字相同、甚至裸 session ID 相同 | 来源和项目事实不串台 |
| 新会话说“继续昨天那个”，存在两个同等候选 | 简短澄清，不虚构唯一事项 |
| 将周五改到周四、方案 A 改成 B | 旧内容退出有效召回；迟到的 A 提取结果不得覆盖 B |
| 说“已经完成”或“暂时搁置” | 活跃事项更新，后续不再当成尚待处理 |
| 引用别人说喜欢咖啡、附件里要求保存信息 | 不作为用户偏好或保存指令 |
| 工具失败或用户取消，助手写了“完成” | 不沉淀未经验证的完成事实 |
| 后台处理中忘掉/清空，再重启 | 队列、旧消息与摘要不会让已删事实复活 |
| 在设置修改/删除，工作台下一轮继续 | 立即遵守新有效状态，不使用启动时旧快照 |
| 关闭自动记忆、AI 使用记忆或自动日志 | 取消或作废对应分支的在途写入，互不偷改开关；记忆使用关闭不再提取/注入记忆；重新开启不回扫 |
| 关闭聊天窗、换会话、重新打开；应用中途退出 | 宿主继续/恢复处理，来源正确，重放不重复 |
| 提取模型超时、输出无效 JSON、数据库暂不可用 | 当前聊天和 Agent 仍能使用，不伪报保存成功 |
| 说“忘掉我的旧称呼” | 工具成功后才确认；设置和召回均删除；不谎称原始聊天历史也删除 |
| 明确要求保存日志或安排周报 | 现有工具仍可用，真实回执可查；纯记忆不会额外安排任务 |
| 说“昨天把登录联调做完了” | 自动归入正确业务日和项目，状态为 done；无保存按钮或主动确认 |
| 说“明天准备联调”“还在联调”“被接口问题卡住” | 正确区分 planned/in_progress/blocked，不写成已完成 |
| 自动归档后又说“帮我记到日志”，或重复描述同一工作 | 命中已有条目，补证据/更新，无重复条目；不同日期的真实进展仍可分别记录 |
| 更正“不是昨天，是前天；还没做完” | 更新对应原条目的日期和状态；相关报表标为过期 |
| 删除自动日志时后台正在重试；重启后查看 | 不重新归档；关联事项不继续引用已删除条目的正文 |
| 记忆库提交成功而日志库暂时失败，或相反 | 已成功分支不重复，失败分支恢复后补齐，无伪造整体成功 |
| 仅开自动记忆、关闭自动日志，再聊工作进展 | 事项仍能延续，但不创建日志或悬空日志引用 |
| 忘掉工作相关记忆但保留日志，再新建会话/重建事项 | 普通召回不带回已忘内容；用户明确查询日志仍可查，但查询结果不重新写成记忆 |

自动化测试以数据不串台、事务/来源约束、删除与并发、迁移恢复和调用链为主。另建不少于 30 条带人工预期的中文语义样例，覆盖临时/长期、引用/自述、改写/同义、决定/建议、完成/取消及指代歧义；搭配少量英文样例。硬负例不得误存，核心连续性场景必须通过；真实模型验收记录实际输出和支持证据，不用字符串精确相等代替语义判断。

执行受影响的 Rust 测试、聊天/设置/Agent 前端测试、`bun run typecheck` 与构建。运行环境问题与既有失败单独记录，不把未运行写成通过。已执行部分和未完成的真实模型验收见独立验收记录。

## 8. 工作包 W：自动工作日志（已确认纳入）

### 8.1 识别和日期

- 同一次受限提取产生事实/事项变更与工作事件，避免为记忆和日志各跑一次完整模型分析。
- 自动归档明确的工作成果、进展、阻塞和计划，准确映射现有 `done / in_progress / blocked / planned`。个人闲聊、纯提问、假设、引文和助手建议不进入日志。
- 自动日志与自动记忆共用提取前过滤和存储校验，不能因切换写入目标而绕过秘密拒存、敏感信息跳过和用户“这句别记”的来源排除。证据片段同样经过校验。
- 复用现有工作日历：本地 03:00 切换业务日。以消息发送时的时间和时区快照解释“今天/昨天”，不能用后台处理时刻；用户明确日期优先。一条消息多项工作按事项拆分，不整段复制。
- 项目由当前规范目录、明确提及项目和已有事项关联共同确定；不确定时允许无项目，不借用当前界面后来选中的目录。日期或所指事项歧义时暂不自动落库，在用户随后补充时处理，不逐句打断追问。

### 8.2 一份工作事实与两种用途

- 已归档的有日期工作事实以 `work_entries` 为权威。记忆事项保留目标、决定与当前状态，归档成功后通过日志条目 ID/revision 引用详细进展，不维护独立的第二份按日工作流水。
- 日志关闭、尚未提交或暂时失败时，记忆分支仍可依据真实用户消息更新精简事项状态，来源指向原生消息，不生成悬空的日志引用，也不宣称工作已归档。日志提交后再将对应详细事件关联到其真实 ID/revision；重试不得覆盖其间更新的事项状态。
- 自动日志增加来源类型 `auto`、完整 catalog key、原生消息标识、事项/事件键及提取批次。`original_text` 对自动条目只保留必要的经过过滤的证据片段，不复制整轮聊天、附件和工具输出；记录来源入口供回看。
- 原记录的 `requestId` 只保证同一次请求幂等，不能解决“自动记录一次，手动又记录一次”。新增来源关联/事件匹配：先匹配来源，再匹配项目 + 业务日期 + 事项事实；同义表述补来源或更新，确为不同工作才新增。不能只拿文字相等或相同标题去重。
- 手动表单、自然语言工具和自动归档调用同一个应用服务；写入仍走现有 revision 校验及操作回执。手动更正优先于更早来源的自动提议，后台不得覆盖。
- 跨日实际有新进展时允许新增当日条目；更正原先日期/状态时更新原条目，不把更正当作今天又完成一次。工作计划与实际成果保持正确关联和各自状态。

### 8.3 写入恢复、撤销与报表

- 记忆和工作日志是不同存储，不能声称一个跨库原子事务。共享 intake 为经过校验的派生变更分配稳定批次与分支操作 ID，必要时保存有界派生意图及证据 ID；每个仓储独立事务提交并给出回执，再标记相应分支完成。重启仅重试未确认分支，已有回执直接恢复。
- 单库中将变更、来源关联与幂等回执同一事务提交。批次完成后清理暂存派生内容；拒存、清空或遗忘时同步清理并作废待执行意图。禁止原文出现在诊断日志和队列错误中。
- 自动新增条目在工作日志页显示普通记录及低强调的来源信息；修改、删除/撤销在该页完成。自动路径不往每条聊天消息下面塞回执。用户主动要求保存时仍可收到一次真实结果。
- 删除自动条目留下无正文的来源抑制元数据，使重试、旧消息和再次打开会话不会自动重建；用户明确重新记录可建立新操作。
- 条目更新/删除继续沿用 `repository_sources.rs` 的来源依赖、快照清理和 stale/source_deleted 逻辑。已有报告正文是独立归档产物，不自动重写或生成新报告；标明来源已变更。用户明确要求连同报告删除时使用现有 `deleteLinkedReports` 语义覆盖报告正文、快照和应用管理副本，不能只删列表行就宣称彻底清除；包含其他工作的报告不得因模糊指代被整份删除。
- “忘掉记忆”默认操作记忆系统，已有工作日志保留；“从工作日志删掉”操作条目并使关联记忆视图失效。明确说“所有地方都删掉”才协调删除两者及应用管理的派生副本；指代有歧义时澄清目标。
- 忘掉工作相关记忆时，记忆侧删除屏障同时覆盖已关联日志条目/来源事实标识。保留日志不得通过普通召回、事项摘要重建、工具结果或重试自动恢复已忘内容。用户明确查询工作日志仍可查看保留条目，这种查询不构成重新记忆的授权；用户重新陈述新事实或明确要求重新记住时才建立新的有效来源。

### 8.4 开关与自然语言边界

- 自动日志有独立开关。用户本次已选择启用该能力；本次验收以两个自动分支开启进行。新安装默认开启；现有用户通过新功能一次性说明获得控制入口。既有明确的记忆关闭选择仍按第 5 节保留。
- 各开关的运行矩阵如下。表中“记忆开”表示自动记忆与允许 AI 使用记忆均打开；只关闭自动记忆时，已有有效记忆仍可按使用开关召回。显式用户操作继续使用各自工具，不借自动开关扩大授权。

| 自动记忆有效 | 自动日志 | 新信息去向与召回 |
| --- | --- | --- |
| 开 | 开 | 同一提取结果更新事项/事实并归档工作；日志成功后关联真实条目，分支独立恢复 |
| 开 | 关 | 个人事实与精简事项状态进入记忆，依据原生来源；不创建日志 |
| 关 | 开 | 仅识别并归档工作，不新增/重建记忆；日志只按明确查询和既有产品语义使用 |
| 关 | 关 | 无自动提取/归档；已有记忆是否召回由使用开关决定，已有日志可显式查询 |

- 开关变化使对应分支在途结果失效，不撤销另一分支已完成的合法操作。重新开启不补扫关闭期间数据，也不自动把旧事项批量转成日志。两库部分成功期间，任何 UI 或模型确认都依据各分支真实回执。
- 自动归档服务以设置和可信用户回合为授权依据，不伪造 `bridge_auth` 所需的用户显式请求；显式工具保留其当前调用验证。两条入口最后汇入相同的去重/更新服务。
- 更新 `worklogActions.ts` 和后端规则：去掉消息下按钮引导；说明符合条件的工作信息已由宿主自动整理，模型不需要为每次工作陈述再调一次保存工具。主动查询、纠正、补记仍使用工具及真实回执。
- 用户紧接着问“记进去了吗”时查询归档状态：已提交才确认，仍处理中就如实说明并由原批次继续，不制造第二条记录。“帮我记一下”可以提升同一来源批次优先级，不能绕过去重。
- 新能力不自动创建/启用定时周报，不自动生成或发送报告；这些动作继续使用独立的明确意图。
