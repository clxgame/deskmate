# macOS 真正一键更新：Sol 5.6 施工任务书

状态：本地实现与隔离 A→B 验证已完成；尚未提交、推送、打标签或发布。正式发布前仍需使用与生产公钥匹配的更新私钥，并完成公证包验收。
需求确认日期：2026-09-20。基于当前 v0.4.3 代码检查；施工前重新核对工作区与依赖版本。

## 1. 用户目标与不可改变的交互

用户要的是一次点击完成检查、下载、安装、重启，不是先点“检查更新”再点“更新并重启”。

- 设置页只保留一个主按钮：**一键更新**。
- 按钮旁常驻简短说明：“有新版时将自动下载安装并重启”。点击即授权这一整次流程。
- 无新版：显示“已是最新版本”，不下载、不退出。
- 有新版：自动推进；不得停在“发现新版”等待第二次确认。
- 不打开浏览器、Finder 或 DMG，不要求拖拽、不要求用户手动退出或再次点击重启。
- 重启后显示实际运行版本，并可显示一次“已更新至 vX”提示；不要在新进程成功运行前宣告完成。
- 系统管理员授权属于可能的系统限制，不伪装成完全无交互；通常的可写安装路径不应触发额外授权。

内部流程可分阶段/API，但前端只有一个操作入口：

```text
一键更新 → 检查 → 下载 → 校验 → 等待安全安装时机 → 安装 → 自动重启 → 新版确认
              └ 无新版 → 已是最新
任一阶段失败 → 明确错误 + 可安全重试（不可误报成功）
```

正在执行任务时：允许先下载与校验，随后显示“等待当前任务结束后自动更新”；完成后自动继续，不需要再点击。等待期间不阻止当前任务推进；安装临界区才暂停新任务入口，并重新原子检查空闲状态，避免竞态。提供取消等待的可选动作。正常成功流程不经过取消或重试按钮。

首期不做：后台定时静默更新、增量更新、Intel/Universal 新增支持、完整更新中心、新版任意业务故障自动降级。保持现有 Windows 更新可用。

## 4. 工作包 A：先解决关键可行性问题

先完成以下只读核对与小规模隔离验证，再实现界面：

1. 确认 Cargo.lock 中的 Tauri/updater 版本及其 Mac 安装与重启实现，不凭最新文档假定本项目行为。
2. 确认现有 updater 公钥对应的私钥是否能用于最终 Mac 包签名，只确认安全使用路径，不展示密钥。GitHub Secret 不能反向读取。若本机没有匹配私钥，记录需要维护者安全配置；继续无密钥依赖的开发，不自行轮换现有 Windows 公钥。
3. 核对活动任务判断、退出保存、sidecar 生命周期；列明安装临界区必须暂停的启动入口。
4. 优先复用 Tauri 官方检查、下载与签名校验。Mac 安装失败恢复必须另行证明，不能把调用 `download_and_install` 等同于事务安全。

特别风险：已检查的 updater 2.10.1 Mac 实现会将旧 App 移至临时目录后替换；相关错误分支没有显式完整恢复，提权分支还有先删除旧 App 再移动新 App 的逻辑。因此禁止直接照搬后宣称“失败会自动回滚”。

安装策略按以下顺序选定，并在施工记录中说明：

- 先确认可用插件版本/接口是否能满足恢复与路径安全要求；若需升级，只做有证据的最小升级并回归 Windows。
- 若仍不满足，在 Mac 安装边界补齐最小必要的持久备份、阶段记录与失败恢复；不重写整个更新框架、不修改本机 Cargo 缓存冒充仓库修复。
- 任一替换操作前验证目标路径、候选包身份、空间与权限；备份不得依赖遇错即自动删除的临时目录。替换失败自动尝试恢复；恢复失败保留备份及明确恢复指引。
- 同卷暂存/替换优先，显式处理跨卷、只读 DMG、App Translocation、含空格/引号路径。不得拼接不安全的特权 shell 删除命令。
- 进程中断后的恢复边界必须说明：普通错误自动恢复；断电/强杀后旧版至少仍有持久可恢复副本，不能承诺没有外部恢复进程也能在应用缺失时自行启动。

如安全安装必须引入常驻提权服务或显著扩大架构，暂停该部分说明取舍，不能悄悄引入。不能保证安全的安装位置，在修改原 App 前明确拒绝，而非冒险替换。

## 5. 工作包 B：客户端单次操作与状态机

主要文件：

- `src-tauri/src/updater.rs`、`src-tauri/src/updater/macos.rs`、对应 Rust 测试。
- `src-tauri/src/lib.rs` 的命令注册与退出流程，必要的任务启动协调点。
- `src/lib/updater.ts`、`src/settings/UpdateFooter.tsx`、`src/settings/updateState.ts`。
- `src/settings/updateErrors.ts`、`src/lib/i18n.ts` 及对应测试。

实施要求：

1. 保留单次 `update_app` 入口或等效编排入口，点击一次自动执行全过程；不要实现成“先 check，再等待用户 install”。
2. 检查结果、选中版本、平台、下载地址与签名由后端管理；不信任前端传入任意安装 URL。限定调用窗口/权限，继续使用经校验的仓库配置和 HTTPS。
3. 同一操作固定目标版本，后续步骤不能因 latest 改变而混用另一个包或签名。拒绝不适用架构及默认降级。
4. 下载后先完成真实性/完整性校验，再等待任务结束、进入安装临界区；不要在下载失败时已经关闭应用。
5. 全应用互斥，防双击、多窗口与并发请求。更新状态由后端持有；设置页关闭再打开能查询当前阶段，不能因前端 Channel 消失而启动第二次安装或丢失流程。
6. 状态至少覆盖 checking、downloading、verifying、waitingForIdle、installing、restarting、upToDate、error；无 Content-Length 时显示不定进度，下载 100% 不等于安装完成。
7. 复用正常退出清理，优先选择能触发生命周期事件的重启接口；明确处理重启失败，不遗留重复 sidecar。不要对不支持续跑的任务宣称可恢复执行。
8. 安装前验证 bundle identifier、版本和 arm64 架构等身份信息，避免只改文件名便接受错误 App。持久状态只记录必要元数据，避免泄漏用户内容。
9. 移除 Mac 正常流程的手动下载按钮及提示；旧下载逻辑若无调用方可清理，不能留下默认回退到“拖拽安装”的成功分支。

## 6. 工作包 C：最终包与发布清单

主要文件：

- `scripts/release-macos.sh`、`scripts/package-macos.sh`。
- `scripts/verify-macos-app.sh`、`scripts/verify-macos-downloads.sh`、必要的新增 updater 验证脚本。
- `scripts/publish-macos.sh`、`.github/workflows/release.yml`、`scripts/macos-release.test.ts`。
- `src-tauri/tauri.macos.conf.json`、`docs/macos-release.md`、`docs/macos-runtime-checks.md`。

保持本机 Apple 签名流程，最终顺序：

```text
候选 App → 修正可移植依赖 → Developer ID 签名 → 公证通过并装订票据
→ 打包最终 App 的 updater tar.gz → Tauri 更新签名 → 解包复验
→ 上传草稿资产 → 合并并验证 latest.json → 发布前验收 → 经授权公开
```

- Mac 新增 `YUME_<version>_aarch64.app.tar.gz` 与 `.sig`；继续提供 DMG 和兼容现有用户的 ZIP。
- tar.gz 必须使用插件期望的单一 `.app` 根目录布局；保持可执行权限与符号链接；检查归档路径安全。
- 不从未签名候选生成公开更新包；不是简单翻转 `createUpdaterArtifacts`。在现有本机最终化阶段生成并签名，或证明调整后的 bundler 顺序等价。
- 签名覆盖最终归档字节；签名完成后不得再修改归档。解包后复查 Developer ID、Team ID、bundle ID、版本、架构、公证和依赖可移植性，并与 DMG/ZIP 内容对照。
- `latest.json` 合并 `darwin-aarch64`，填入真实归档 URL 和 `.sig` 文件内容，不是 `.sig` 的 URL。保留已有 Windows 平台条目；使用程序解析合并，不字符串拼接。
- 统一一个最终清单写入者，避免 Windows CI 与本机脚本互相覆盖。脚本只允许操作草稿：先全部上传及校验，再写最终清单；失败时保持未发布，不让用户拿到半成品版本。
- 验证清单版本、URL 中的 tag、App 内版本一致，以及引用的资产实际存在；完整性验证通过不等于签名、公证通过。
- 更新校验和文件，严格列出预期公开资产；不得把缓存、日志、私钥或未签名候选一起上传。
- Windows 已有资产及签名不可被 Mac 发布步骤重签、替换或删除；脚本重跑需能识别一致的已有草稿资产，冲突时拒绝，不用无条件覆盖。

## 7. 工作包 D：验证矩阵与通过条件

自动测试必须覆盖：

| 场景 | 必须满足 |
| --- | --- |
| 新版可用 | 只点击“一键更新”一次，自动推进到重启；浏览器打开调用为零 |
| 无新版 | 显示最新，不下载、不安装、不重启 |
| 下载/清单/签名错误 | 明确分类错误，原 App 未改，锁释放，可重试 |
| 双击、多窗口、重新打开设置 | 只有一个更新任务，进度可恢复显示 |
| 正在运行任务 | 不强杀；任务结束后自动继续，无第二次确认；可取消等待 |
| 不兼容架构/身份、缺 Mac 资产 | 明确拒绝，不误报最新，不安装错误包 |
| 空间、权限、安装或恢复错误 | 故障注入证明保留可恢复旧 App；不误报成功 |
| 清单合并与脚本重跑 | Windows 条目不丢失；不覆盖公开 Release；错误资产无法发布 |
| 正常重启 | 清理执行一次，旧进程退出，新进程版本正确，无重复 sidecar |

先建立现有测试基线，再运行相应检查（以仓库实际命令为准）：

```bash
bun run typecheck
bun test src/settings/UpdateFooter.test.tsx src/settings/updateState.test.ts src/settings/updateErrors.test.ts
bun test scripts/macos-release.test.ts
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib updater
bun test
bun run build
```

新增测试文件也必须执行。Windows 至少编译相关条件分支并跑更新回归，不能把 Mac 构建通过当跨平台验证。

真实升级验收：

- 在隔离安装位置、隔离用户数据和测试更新源上，制作两份真实签名公证的 A/B 测试版本。
- A 必须已包含新 updater；单击 A 的“一键更新”，自动变成 B 并重启，验证桌宠、设置、数据、sidecar、签名与公证。
- 使用内部端点注入/测试构建配置，不占用正式 latest，不默认公开测试版本；生产配置不得留下关闭 TLS/签名校验的后门。
- 仓库提供的 `updater-qa` Cargo feature 只接受编译时注入的 loopback HTTP endpoint；正式构建不启用该 feature，也不允许普通设置绕过 HTTPS。
- 覆盖普通可写位置及需要授权的位置；含空格路径、只读 DMG、网络失败、取消授权、安装失败要有实测或可重复故障注入证据。
- 如果证书、更新签名私钥或受控测试源不可用，明确标记“实机升级未验证”，不能以 mock 通过宣称交付完成。

发布门槛：相关测试通过、原有失败有明确处理结论、最终包验证通过、A→B 一键升级实测通过、Windows 回归通过。任何未完成项都列明，不绕过发布检查。

## 8. 迁移与施工交付

- v0.4.1/v0.4.3 的旧 Mac 客户端没有自动安装代码，必须最后手动安装一次迁移版；无法仅改远端清单补出旧客户端能力。
- 迁移版之后才是本任务定义的真正一键更新。不要将此前旧版手动迁移说成正常更新仍需两步。
- 新版本号在发布时确定，不覆盖 v0.4.3，不先发布一个暂时无法完成自动更新的半成品。
- 建议按“客户端与测试 / 安全安装与恢复 / 发布包与清单 / 文档与验收记录”组织改动；未经另行授权不提交推送或正式发布。

Sol 5.6 最终交付应包含：改动摘要、测试结果及基线差异、A→B 实测证据、失败恢复边界、密钥配置剩余项、明确的待发布状态。没有执行的测试必须直说未执行。
